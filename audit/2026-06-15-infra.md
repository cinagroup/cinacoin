# Cinacoin 基础设施层审计报告

**审计日期:** 2026-06-15  
**审计员:** AI Infrastructure Auditor  
**审计范围:** 基础设施层（RPC Proxy, Relay Server, Keys Server, Push Server, Notify Server, Analytics Server, Blockchain API, Explorer, TX Indexer, Monitoring, CDN, Deploy）

---

## 执行摘要

### 总体评分: **7.8/10** ⭐⭐⭐⭐

Cinacoin 基础设施层展现出**成熟的 Cloudflare 原生架构**，充分利用了 Workers、KV、D1、Durable Objects 等核心服务。双版本（Node.js/Rust + Cloudflare）策略提供了优秀的灵活性和性能优化空间。安全性、可观测性和成本控制方面表现良好，但在高可用、部署自动化和部分模块的 Cloudflare 集成深度上仍有改进空间。

### 关键发现

**✅ 优势:**
- Cloudflare 集成度高（8/10）：5 个核心服务已迁移到 Workers
- 安全性扎实（8/10）：认证、速率限制、CORS 全面覆盖
- 可观测性完善（7.5/10）：Prometheus 指标、健康检查、结构化日志
- 性能优化到位（8/10）：多层缓存、连接池、请求去重
- 成本控制意识强（7/10）：预算告警、Spot 实例、KEDA 自动扩缩

**⚠️ 改进空间:**
- 高可用架构待加强（6.5/10）：缺少跨区域故障切换和优雅降级策略
- 部署自动化不足（6/10）：缺少 CI/CD 流水线、回滚策略和蓝绿部署
- 部分模块未充分利用 CF 特性（7/10）：Queues、R2、Durable Objects 使用有限
- 文档和测试覆盖不均（7/10）：核心模块完善，边缘模块薄弱

## 详细分析

### 1. RPC Proxy（RPC 代理）

**模块概览:**
- **实现:** Go 版本 + Cloudflare Worker（TypeScript）双版本
- **功能:** 多链 JSON-RPC 代理，支持 10+ 条链（Ethereum、Solana、TRON、TON、Sui、Cosmos、NEAR 等）
- **部署:** `rpc.cinacoin.com`（Workers 自定义域名）

**Cloudflare 集成度: 9/10** ⭐⭐⭐⭐⭐
- ✅ **KV 缓存:** 读-only 方法缓存（TTL 可配置，eth_blockNumber 12s，eth_chainId 3600s）
- ✅ **速率限制:** KV 持久化跨实例速率限制（100 RPM/IP）
- ✅ **Workers 原生:** 完全使用 Workers 运行时，无外部依赖
- ✅ **边缘缓存:** 利用 CF 全球边缘网络，延迟极低
- ⚠️ **未使用:** R2（可用於大响应缓存）、Queues（可用於异步批处理）

**高可用: 7/10** ⭐⭐⭐⭐
- ✅ **Fallback 链:** 每条链配置多个 fallback RPC（如 Ethereum: cloudflare-eth.com → ethereum.publicnode.com → rpc.mevblocker.io）
- ✅ **健康检查:** `/health` 端点返回支持的链列表
- ⚠️ **无自动故障切换:** Fallback 是顺序尝试，非并行健康检查
- ⚠️ **无熔断机制:** 上游失败后仍会尝试所有 fallback
- ❌ **缺少:** 跨区域部署、负载均衡、优雅降级

**安全性: 8.5/10** ⭐⭐⭐⭐⭐
- ✅ **CORS:** 严格限制到 cinacoin.com 子域名
- ✅ **速率限制:** 每 IP 100 RPM，KV 跨实例持久化
- ✅ **安全头:** X-Content-Type-Options、X-Frame-Options、CSP、HSTS
- ✅ **输入验证:** JSON-RPC 格式校验、方法白名单
- ⚠️ **无 API Key 认证:** 依赖速率限制而非认证（适合公开 RPC）

**性能: 9/10** ⭐⭐⭐⭐⭐
- ✅ **多层缓存:** 内存 LRU + KV 持久化
- ✅ **细粒度 TTL:** 每个方法独立 TTL（eth_blockNumber 12s，eth_chainId 3600s）
- ✅ **请求去重:** Go 版本支持 in-flight 请求去重
- ✅ **连接池:** Go 版本 HTTP 连接池（MaxIdleConnsPerHost: 20）
- ✅ **缓存命中率:** 指标暴露 cache_hits/cache_misses

**可观测性: 8/10** ⭐⭐⭐⭐⭐
- ✅ **Prometheus 指标:** 请求数、错误数、缓存命中率、上游延迟、按链统计
- ✅ **健康检查:** `/health` 返回状态、版本、运行时间
- ✅ **结构化日志:** 使用 `@cinacoin/logger`，包含 requestId
- ⚠️ **缺少:** 分布式追踪（可集成 Cloudflare Workers Analytics Engine）

**部署: 6/10** ⭐⭐⭐
- ✅ **Wrangler 配置:** 完整的 `wrangler.toml` 和 `wrangler.production.toml`
- ✅ **部署脚本:** `deploy-rpc-proxy.sh` 支持 staging/production、dry-run
- ⚠️ **无 CI/CD:** 手动部署，缺少 GitHub Actions/GitLab CI
- ❌ **无回滚策略:** 缺少 `wrangler rollback` 自动化
- ❌ **无蓝绿部署:** 直接覆盖部署

**成本: 8/10** ⭐⭐⭐⭐⭐
- ✅ **缓存优化:** 高缓存命中率减少上游请求
- ✅ **Workers 免费额度:** 10 万请求/天免费
- ⚠️ **KV 读写:** 高频缓存可能产生 KV 操作费用（需监控）

**问题清单:**
1. **[P2]** 缺少熔断机制，上游故障时仍尝试所有 fallback
2. **[P2]** 无 API Key 认证，依赖速率限制（适合公开 RPC，但不适合内部服务）
3. **[P3]** 未使用 R2 存储大响应（如 eth_getLogs 大批量结果）
4. **[P3]** 缺少 CI/CD 流水线和自动回滚

**优化建议:**
1. **添加熔断器:** 使用 `stale-while-revalidate` 模式，上游失败时返回过期缓存
2. **集成 Cloudflare Rate Limiting API:** 替换 KV 速率限制，减少 KV 操作
3. **使用 R2 缓存大响应:** 对超过 1MB 的响应使用 R2 存储
4. **建立 CI/CD:** GitHub Actions 自动测试 + 部署 + 回滚

### 2. Relay Server（中继服务器）

**Cloudflare 集成度: 8.5/10** ⭐⭐⭐⭐⭐

- ✅ **KV 缓存:** 会话元数据缓存
- ✅ **Workers WebSocket:** 原生 WebSocket 支持
- ⚠️ **未使用:** D1（可用於会话历史）、Queues（可用於异步消息投递）

**高可用: 7.5/10** ⭐⭐⭐⭐
- ✅ **Redis Pub/Sub:** 跨实例消息同步
- ✅ **心跳机制:** 30s 心跳，60s 超时
- ✅ **主题过期:** 自动清理过期主题
- ⚠️ **单点依赖:** Redis 故障会影响跨实例同步
- ❌ **缺少:** 多区域部署、自动故障切换

**安全性: 8/10** ⭐⭐⭐⭐⭐
- ✅ **CORS:** 严格限制
- ✅ **速率限制:** 每 IP 连接速率限制
- ✅ **消息大小限制:** 防止大消息攻击
- ✅ **主题验证:** 防止无效主题
- ⚠️ **无加密验证:** 依赖客户端 E2E 加密（符合 WalletConnect 设计）

**性能: 8.5/10** ⭐⭐⭐⭐⭐
- ✅ **广播通道:** 内存 broadcast channel（容量 1024）
- ✅ **Redis Pub/Sub:** 跨实例消息投递
- ✅ **消息指标:** 消息大小、投递延迟
- ⚠️ **广播通道瓶颈:** 1024 容量可能在高并发下丢失消息

**可观测性: 8/10** ⭐⭐⭐⭐⭐
- ✅ **Prometheus 指标:** 活跃连接、订阅数、消息发布/投递数、协议错误
- ✅ **健康检查:** `/health` 端点
- ✅ **结构化日志:** 连接建立/关闭、订阅/取消订阅

**部署: 6.5/10** ⭐⭐⭐
- ✅ **Wrangler 配置:** 完整的 DO 绑定
- ✅ **部署脚本:** `deploy-relay-server.sh`
- ⚠️ **DO 状态管理:** 缺少 DO 实例迁移策略
- ❌ **无 CI/CD**

**成本: 7.5/10** ⭐⭐⭐⭐
- ✅ **DO 按需计费:** 按实际使用计费
- ⚠️ **WebSocket 长连接:** 可能产生较高的 DO 持久化费用

**问题清单:**
1. **[P2]** 广播通道容量有限（1024），高并发下可能丢失消息
2. **[P2]** Redis 单点依赖，故障会影响跨实例同步
3. **[P3]** 缺少 DO 实例迁移和状态备份策略

**优化建议:**
1. **增加广播通道容量:** 或实现消息持久化（D1/KV）
2. **Redis 集群:** 使用 Redis Cluster 提高可用性
3. **DO 状态备份:** 定期将会话状态备份到 D1

### 3. Keys Server（密钥管理服务器）

**模块概览:**
- **实现:** Node.js/Rust + Cloudflare Worker 双版本
- **功能:** 密钥管理（身份密钥、邀请密钥、钱包密钥），AES-256-GCM 加密
- **部署:** `keys-server.cinacoin.com`

**Cloudflare 集成度: 8/10** ⭐⭐⭐⭐⭐
- ✅ **KV 存储:** 加密密钥存储
- ✅ **Web Crypto API:** Workers 原生加密（AES-GCM、PBKDF2、HMAC）
- ✅ **速率限制:** KV 持久化
- ⚠️ **未使用:** D1（可用於密钥元数据和审计日志）

**高可用: 7/10** ⭐⭐⭐⭐
- ✅ **健康检查:** `/health` 检查数据库和 Redis
- ✅ **优雅降级:** 数据库/Redis 故障时返回 "degraded" 状态
- ❌ **缺少:** 多区域部署、自动故障切换

**安全性: 9/10** ⭐⭐⭐⭐⭐
- ✅ **JWT 认证:** HS256 签名验证
- ✅ **AES-256-GCM:** 强加密算法
- ✅ **PBKDF2:** 密钥派生（100k 迭代）
- ✅ **恒定时间比较:** 防止计时攻击
- ✅ **CORS:** 严格限制
- ✅ **速率限制:** 100 RPM/IP
- ⚠️ **密钥轮换:** 支持但缺少自动轮换策略

**性能: 7.5/10** ⭐⭐⭐⭐
- ✅ **KV 缓存:** 密钥元数据缓存
- ⚠️ **加密开销:** PBKDF2 100k 迭代可能较慢（Workers CPU 限制 10ms/30ms）
- ⚠️ **无连接池:** Node.js 版本缺少数据库连接池

**可观测性: 7.5/10** ⭐⭐⭐⭐
- ✅ **Prometheus 指标:** 请求数、密钥创建/检索/删除/轮换数、认证失败
- ✅ **健康检查:** 数据库和 Redis 健康状态
- ⚠️ **缺少:** 审计日志（密钥操作应记录到 D1）

**部署: 6/10** ⭐⭐⭐
- ✅ **Wrangler 配置:** 完整
- ✅ **部署脚本:** `deploy-keys-server.sh`
- ❌ **无 CI/CD**
- ❌ **无密钥轮换自动化**

**成本: 8/10** ⭐⭐⭐⭐⭐
- ✅ **KV 存储:** 低成本
- ⚠️ **加密 CPU 开销:** 可能接近 Workers CPU 限制

**问题清单:**
1. **[P1]** PBKDF2 100k 迭代可能超过 Workers CPU 限制（10ms/30ms）
2. **[P2]** 缺少审计日志，密钥操作无法追踪
3. **[P3]** 无自动密钥轮换策略

**优化建议:**
1. **降低 PBKDF2 迭代:** 或改用 Argon2（Workers 不支持）
2. **集成 D1 审计日志:** 记录所有密钥操作
3. **自动密钥轮换:** 定期轮换加密密钥

## 优先级问题清单

### P1（高优先级）

1. **Blockchain API 未迁移到 Workers**
   - **影响:** 性能差、成本高、无法利用 CF 全球边缘网络
   - **建议:** 迁移到 Workers + KV 缓存

2. **TX Indexer 未迁移到 Workers**
   - **影响:** 需要服务器成本、无法利用 CF 服务
   - **建议:** 迁移到 Workers + D1 存储索引数据

3. **Keys Server PBKDF2 迭代过高**
   - **影响:** 可能超过 Workers CPU 限制（10ms/30ms）
   - **建议:** 降低迭代次数或改用更快的 KDF

### P2（中优先级）

4. **缺少统一 CI/CD 流水线**
   - **影响:** 手动部署、易出错、无自动回滚
   - **建议:** 建立 GitHub Actions 编排所有服务

5. **缺少自动回滚策略**
   - **影响:** 部署失败需要手动回滚
   - **建议:** 集成 `wrangler rollback` 到 CI/CD

6. **RPC Proxy 缺少熔断机制**
   - **影响:** 上游故障时仍尝试所有 fallback
   - **建议:** 添加熔断器，失败时返回过期缓存

7. **Relay Server 广播通道容量有限**
   - **影响:** 高并发下可能丢失消息
   - **建议:** 增加容量或实现消息持久化

8. **Push Server 批量推送顺序执行**
   - **影响:** 性能较差
   - **建议:** 使用 `Promise.all` 并行投递

9. **Notify Server 同步投递**
   - **影响:** 可能阻塞请求
   - **建议:** 集成 Queues 异步投递

10. **Blockchain API 无缓存**
    - **影响:** 每次请求都调用 RPC，性能差
    - **建议:** 添加 KV 或 Redis 缓存

### P3（低优先级）

11. **缺少分布式追踪**
    - **影响:** 难以追踪跨服务请求
    - **建议:** 集成 Cloudflare Workers Analytics Engine 或 OpenTelemetry

12. **Keys Server 缺少审计日志**
    - **影响:** 密钥操作无法追踪
    - **建议:** 集成 D1 记录所有操作

13. **Explorer 缺少服务端组件**
    - **影响:** 无法独立优化
    - **建议:** 考虑使用 Workers + KV 缓存钱包注册表

14. **Monitoring 未使用 CF Analytics Engine**
    - **影响:** 需要自建 Prometheus
    - **建议:** 集成 CF Analytics Engine

15. **CDN 缺少使用统计**
    - **影响:** 无法追踪 SDK 使用情况
    - **建议:** 集成 Analytics Server
